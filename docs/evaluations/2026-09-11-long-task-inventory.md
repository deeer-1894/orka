## 主要问题与证据

### 1. 输出限额止住长生成，但仍会花大量时间在纯思考及截断重试

首轮在58.0592秒用完4096输出tokens，全部为reasoning，未形成工具调用；9.6365秒重试后才开始建计划。下一次生成127.3724秒、8192输出tokens也全为reasoning，重试11.1266秒才写出common.py。第三次在128.7734秒再次用完8192纯思考tokens，随后重试51.227秒耗尽该逻辑调用共180秒的期限，整轮失败。

三个被丢弃的length响应合计314.205秒、20,480 reasoning tokens；加最后失败重试，约365.432秒没有形成可接受的新动作。主模型已上报输出中42,966/54,593为reasoning（约78.7%）。这不等于全部思考都无用，也不能把全部模型耗时都称作思考耗时，但足以证明仅设置max_tokens无法保证及时推进。

主模型调用累计880.454秒，摘要34.9436秒，接近整个运行时间。摘要本轮仅一次，不支持把这次慢归因于“频繁摘要”。本轮没有此前首轮500秒以上的无限长生成，但180秒上限会把尚有预算和断点的任务转为failed；上限后的恢复与交付处理仍需优化。

### 2. 验收被放在过晚阶段，错误汇总进入看板

独立oracle完全按提示词生成，先建立基线再读取模型产出；同时用累计供需公式交叉检查状态模拟。raw 1114行×7字段、clean 1080行×7字段、daily 1080行×13字段逐项一致，指定30条重复和4种坏样本正确。36项采购建议和36项P95均精确正确。满足率六位、七日均值四位的显示舍入按原需求允许的合理精度处理，不记作公式错误。

40组×8个指标中312项正确，8项期末聚合错误：

| 分组 | 期末库存：交付 / 正确 | 期末欠单：交付 / 正确 |
|---|---:|---:|
| 总体 | 65 / 441 | 0 / 549 |
| W1 | 15 / 25 | 0 / 342 |
| W2 | 40 / 127 | 0 / 163 |
| W3 | 65 / 289 | 0 / 44 |

交付analyze.py的aggregate取该组最后一条记录的closing值，而需求要求汇总最后一天该组的所有仓/SKU。该错误在首次摘要前已经产生，不能据此认定是摘要改写了要求。简单业务守恒已能检出：需求10,800 = 发货10,251 + 欠单549；初始库存1,296 + 收货9,396 = 发货10,251 + 库存441。

正确的及时满足量为9,547，及时满足率88.398148%，收入28,806,654分，补货建议合计1,924件。采购前五应为W1/S01 119、W1/S02 106、W1/S03 105、W2/S03 96、W2/S01 93；看板存在相应数据，正式report.md未交付。这里区分“数据值正确”和“报告缺失”。

### 3. 图表存在文件不等于可正常打开

charts/replenishment.svg生成了36个开标签`<rect>`却没有对应闭合，XML解析报`mismatched tag: line 100, column 2`。三张SVG的背景尺寸都写成`100%%`，不是有效SVG长度。模型在后期计划中记录了双百分号问题，但直到失败仍未修复。

独立结构与几何审计61项中57项通过、4项失败，包括三处无效百分比和一处XML错误。通过项仅表示图表/HTML与已产出数据的对应关系，不替代业务oracle；看板总体卡片忠实展示了错误的期末指标。本审计没有将未做的浏览器视觉截图检查计为通过。

### 4. 收尾未执行，不能证明完整复现或验证器有效

缺失文件：report.md、verify.py、verification.txt、run_all.py、package.py、README.md、manifest.json、delivery.zip。因此没有一条完整离线复现命令，没有16项实际断言与边界样例交付，也没有封包字节、CRC和摘要验证证据。针对不存在的验证器，变异测试应记not_run，不能报“通过”或“0/N检出”。

补充的隔离复现已实际运行generate、analyze、render三个阶段，均退出0；11个生成文件与原交付逐字节一致，同时重现期末汇总与SVG错误。源码只使用标准库及本地共享模块，职责分拆基本清楚，但仍缺全流程入口。这项部分复现不替代完整交付验收。

最后一次file_write为444.838秒的sources.json，此后约475秒没有新的文件写入。全轮file_read 16次，还包含一次整批脚本shell回读、2次file_list和2次本地证据搜索。重复回读有合理的核对用途，但本轮未能转化为验证器或最终交付，提示需要以实际产物和验收推进判断阶段进度。

### 5. 失败恢复与文件归属显示仍容易误导

运行记录保留断点，但聊天页显示“处理超时了，请重试或简化任务。”，并提示检查工具/沙箱。`web/src/App.tsx:319`的聊天“重试”重新发送最后一条用户输入；真正调用resumeRun的“继续”入口位于运营台。两者不是同一种恢复语义，应在失败处直接呈现可恢复状态、未完成项和继续入口。

运行中“本会话文件”曾显示旧B/E评测目录的generate.py、metrics.json、manifest.json等同名文件。`web/src/components/Thread.tsx:88`按全用户工作区文件名回退匹配，且流式运行不刷新索引，因此把思考中提到的名称匹配到旧文件。终态刷新后显示本轮5个直接file_write产物，但仍未列出全部脚本运行产物。没有证据表明模型实际读取了那些旧评测业务数据；这是已观察到的显示归属问题。

## 调研范围与引用

使用7次fetch_url和1次read_section，共8次远程调研调用；涉及7个官方正文页面（Python 3、SQLite 4），符合上限，2次search_evidence为本地检索，没有付费web_search。调研未出现上一任务的无边界扩展，但4维×2方案的正式比较报告未交付。

sources.json有一处证据错配：它把“单写入者”附在[SQLite事务说明](https://www.sqlite.org/transactional.html)后，该页正文仅支持ACID及中断恢复；单写入者的直接依据在[WAL并发说明](https://www.sqlite.org/wal.html#concurrency)。这是链接支撑范围错误，不是认定该能力不存在。[类型文档](https://www.sqlite.org/datatype3.html)确实区分动态类型和STRICT表；本轮来源记录保留了这一区分。

## 下一步优化顺序

1. 将生成预算与步骤类型绑定，给下一小步持续而明确的执行约束；保留截断响应不执行的完整性保障。调用触限时，在剩余预算和检查点约束内进入可恢复状态，明确未完成项，避免仅泛化成“请重试”。不能简单无限延长超时或开启无限重试。
2. 将用户验收要求转成可执行检查，业务结果生成后立即执行守恒、分组和边界断言，通过后再渲染及撰写报告；结构校验与业务校验分别出结论。
3. 按已验证产物推进阶段，为验证/报告/封包保留时间与预算。对同版本脚本反复整文件回读提供更小的接口摘要和定向读取，避免单凭消息次数判断进度。
4. 将聊天失败入口连接到已有断点恢复，并按run及精确路径归属产物；禁止将缺失的当前文件回退到其他任务同名文件。

本轮没有修改生产实现，上述为依据实测排序的后续工作，不表示已经修复。单次跨业务场景评测不能估计整体成功率，也未覆盖恢复后的后续运行。
