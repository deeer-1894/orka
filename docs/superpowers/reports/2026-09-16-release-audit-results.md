## Orka 前后端优化点

### P1：成果验收需要验证任务约束，而不只是文件存在

`check_delivery` 已明确限定自己负责结构检查，这个边界应保留；不应把任意业务断言塞进通用文件检查器。建议单独设计任务验收契约：约束、证据位置、执行命令、结果、未通过项。执行器与校验器分开，校验器从用户需求与原始证据生成检查，覆盖失败路径。最终的“运行结束”“文件检查通过”“业务约束通过”应分开显示。

验收标准：本报告故障注入用例作为回归样本；不能仅靠生成程序自己的 verify 或计划已全勾选就宣告整体成功。保持编程、调研等具体校验器可插拔，不让聊天编排层了解特定项目字段。

### P1：HTTP 工具静默截断，损坏 JSON 并导致重试

位置：`tools_server/tools/http_request.go:106`。目前读取最多 64 KiB，忽略读取错误，也没有向调用者声明截断。本次 per_page=30 的响应截断，模型自行识别后改为 per_page=10，三个仓库额外重抓。

建议抽出统一响应读取模块，返回状态、内容类型、读取字节数、上限、截断标记和完整证据文件位置；正文摘要与可下载原始证据分离。上限需要保留，不能以无限读响应解决。测试覆盖恰好达到上限、超一字节、流读取错误和非 JSON 响应。

### P1：概览的实时统计和累计统计不可信

本轮预算已用 254,978 tokens 时，“当前会话运行”仍显示 0 tokens / 0 次工具调用；任务结束后该处才变为 865,216 / 51，但“累计指标”依旧全部为 0。

- `web/src/components/MetricsPanel.tsx:30` 直接显示 run 的终态结算字段。
- `orka_control_layer/service/adk_chat.go:448` 在结束时写入 run.tokens/tool_calls。
- `orka_control_layer/obs/obs.go` 的 ObserveLLM/ObserveToolCall 有定义但没有生产调用点；新进程的原子计数不等于持久化历史累计。

建议在统一运行统计服务中定义实时、已结算和用量未知三种口径；前端只消费该服务输出。历史累计从持久记录汇总，进程指标明确标注进程范围。无法获取时显示“暂不可用”，不补零。前端刷新依赖统一运行事件或轮询资源，避免每个面板各自维护统计。

### P2：工作台自动抢焦点

实际切到概览后，后续写文件事件又把工作台切回成果。`web/src/components/ArtifactDrawer.tsx:100` 在 liveTab 变化时强制 setTab，没有记录用户是否已经手动选择过标签。

建议用户手动切换后保留选择，新活动只显示轻提示；自动跟随作为明确的可选模式。相关状态放在工作台自身，不让文件工具控制界面导航。

### P2：文件计数漏掉子文件夹，刷新口径分散

`web/src/components/DashboardPanel.tsx:25` 只统计根目录非文件夹条目，并且 effect 只依赖 conversationID。本次目录已包含多个文件时仍为 0，生成根目录 ZIP 后变为 1；与聊天中的 14 个文件入口显著不一致。

建议提供会话工作区摘要接口，统一非系统文件递归总数、目录数、字节数和版本号，复用文件变更事件刷新。不要让概览递归请求整棵树，也不要用聊天消息中出现的文件路径数量冒充工作区总数。

### P2：文件回执替换了用户要求的最终摘要

本次用户要求最终答复简述版本数、测试数和兼容性限制，但最终只输出文件清单和通用提示。`orka_control_layer/service/delivery_response.go` 在 file_receipt 模式把模型文字整体替换为固定回执。

建议把下载回执与经过核验的简短摘要分别建模；用户明确要求摘要时保留结构化摘要，不通过自由文本重复推算统计，也不一律丢弃结论。回执负责稳定链接，验收结果负责事实，呈现层组合两者。

### 后续成本优化需要先量化

本轮 42 轮累计预算约 86.5 万 tokens；计划更新 9 次，包含重复更新。它提示有上下文重复输入与调度开销，但当前仅有总账，不能据此断言模型“思考太久”就是主因。应先记录每次调用的输入、输出、缓存命中、首字延迟、工具等待和上下文压缩，再针对性减少重复证据注入、避免无变化计划更新。标题调用用量未知应单独调查，不混作已确认消耗。
