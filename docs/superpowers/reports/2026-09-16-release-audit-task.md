# 可复现对比任务：真实版本调研与离线升级审计器

建议对比设置：glm-5.3-flash；Token 上限1500000；时长2400秒；轮次180；启用联网、文件、网页DOM、代码；保留现有高危操作确认策略。以下正文一次性发送，不追加隐藏要求。

---

请完成一次真实的 Python Web 技术栈版本维护调研，并交付一个可以离线运行、复核调研数据的小项目。研究对象限定为 FastAPI、Starlette、Pydantic 三个真实项目。以你开始任务时的 UTC 时间作为观察截止时间，不假设任何线上业务已经采用某个版本。

请自行规划、执行、检查和修复。不要只给方案，也不要编造网页内容、版本号、发布日期、测试结果或数据来源。遇到访问失败需记录真实失败并尝试合理替代官方来源；无法确认的字段留空并说明，不能用猜测填满。

1. 调研与证据：从三个项目的官方仓库发布记录或官方发布说明中，各收集观察截止时间之前最近5个稳定发布版本，共15条；排除预发布和草稿，明确“稳定版本”的判断依据。每条至少含项目、原始tag、版本号、UTC发布时间（如果来源没有则留空）、官方来源URL、变更摘要、是否明确包含破坏性变更及证据。另查官方资料解释三者之间的依赖关系，以及为什么仅凭三个“最新版本”不能证明它们兼容。只报告已核实的约束，别把缺乏证据写成兼容。

2. 保留原始输入：在当前会话工作区 release-audit/ 下保存真正读取的原始响应或网页摘录，以及 provenance.json，记录对应文件、URL、UTC抓取时间、内容SHA-256、是否截断、数据类型。区分网页原文、摘录和你自行整理的字段；无法取得完整原始响应时，不要伪称完整。后面的离线程序只读取这些输入，不依赖网络、API Key或第三方Python包。

3. 实现可维护的Python标准库小项目：把输入解析、版本处理、字段校验、审计统计、导出与命令行入口分开。提供 build 和 verify 两个子命令。build 从保留的输入生成标准化 releases.json、releases.csv、report.md、report.html；版本排序必须正确处理 v 前缀、2.9与2.10、预发布，并保留原始tag。相同项目与版本去重；如果重复记录的关键字段冲突，必须报告错误，不能静默覆盖。时间缺失或无法解析时明确标记，不可默认为今天。

4. HTML报告必须可直接本地打开，包含三项目对比摘要、15条发布记录表、项目筛选、关键词搜索、官方来源链接，以及“兼容性已确认／尚未确认”的清晰说明。不要把网页来源文字当作HTML或脚本执行，CSV也要处理公式注入风险。筛选后的条数要跟表中可见行数一致。

5. 验证与失败行为：verify 校验原始输入哈希、来源记录完整性、每项目版本数、重复冲突、输出表格与JSON记录数一致性、排序与UTC日期有效性。至少实际运行18项有意义的自动测试，覆盖正常流程、版本排序、预发布过滤、重复幂等、重复冲突、坏输入不覆盖既有有效产物、Unicode、CSV引号换行与公式防护、HTML转义、缺失日期，以及CLI成功/失败退出码。少量人工编写的边界测试数据允许使用，但必须标明“测试夹具”，不得混入真实发布数据或冒充真实来源。人工夹具通过不等于真实数据验收通过，两者分别报告。

6. 交付前自查：写README说明从ZIP解压后如何离线重建报告、运行全部测试与verify。写validation.md，记录实际执行命令、测试通过/失败数量、真实数据完整性和已知限制。如果真实来源最终不足15条，要明确列出缺口，verify应反映该状态，不许降低数量要求凑成功。打包release-audit.zip，必须包含离线运行所需的输入、源码、全部测试和最终报告，不含密钥、缓存、虚拟环境。再把最终ZIP解压到不同目录，实际执行README中的命令，证明没有依赖当前工作目录或漏打包文件。

最终答复给出可点击的ZIP、HTML和Markdown下载入口，简述实际采集到的版本数、真实运行的测试数量、仍未证实的兼容性问题；不要把“测试通过”等同于“可以直接升级生产环境”。
