# 发布收尾修复与长任务验证

分支：`codex/long-task-optimization`。本轮继续在右侧 `real@test.com`、`glm-5.3-flash` 运行实际 SQLite 项目的发布流程开发任务；任务全文见 `2026-09-17-release-pipeline-task.md`。

## 产品代码修复

- `orka_core/artifacts/archive_review.go`：在现有ZIP结构验证后，独立检查包内文档的文件引用与嵌套ZIP。仅根据归档成员检查，不使用工作区文件掩盖缺失。结果是 `warnings`，不会把例子或将来生成的输出强制变成交付要求。
- `document_references.go`：提取保守的本地链接、带目录的行内路径；跳过代码围栏、缩进示例、外部URL、通配符等。没有宣称这是完整Markdown语法分析器或业务验收器。限制32份文档、单文档256KiB、总读取2MiB、最多20条具体提示；触限明确报告检查不完整。
- `delivery_incremental.go`：复用同一按文件版本去重的检查入口；既检查已登记的小ZIP，也检查执行服务真实写入回执中的ZIP，不自动声明临时文件为交付物。相同版本不会不断重复输出提示。未展示的信息保留原有延迟检查机制。
- `execution_evidence.go`：实际进程非零退出但没有stdout/stderr时，提示先读已有日志、按需用明确退出码处理和工作区日志恢复；不推测原因、不自动重试、不改变失败状态。拒绝执行、超时、取消不套用这一提示。
- `delivery_response.go`：自动文件收据保留归档审查提示，避免提示被结构检查的成功收据吞掉。
- `web/src/lib/sessionFiles.ts`：本轮声明的交付物排在中间源码之前，仍经现有存在性检查；同一运行的插入消息保留计划，新运行清除旧计划。新消息和插入消息都使用 `human_input`，必须按确切的 `run_id` 判断，不能只看动作名。沿用文件列表与下载按钮样式，不增加额外UI。
- 发布指导补充稳定打包、历史/当前日志区分、最终哈希放包外、先固定内容再验收等规则；没有添加token或执行次数限额。

模块边界：核心归档审查不访问运行状态/数据库；服务层管理真实写入、检查时机和去重；前端仅决定已存在文件的展示顺序，不推断验收结果。
